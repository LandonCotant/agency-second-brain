# ADR 0060 — Signal feedback + suppression loop (teach the agents what's noise)

**Status:** Proposed — 2026-05-31
**Extends:**
- ADR 0034 / 0035 — Risk Watcher follow-up profiles + OwnerDisengagement (this adds a feedback gate in front of flag emission)
- ADR 0037 — single `agent_outputs.*` dataset with a `scope` column (the new `signal_feedback` table lives here, no new dataset)
- ADR 0051 — Brain is a signal substrate; conversation/composition lives behind the MCP seam (feedback is captured conversationally via a new MCP write tool)

## Context

The system surfaces signals well (Risk Watcher → `risk_flags`, Triage → `triaged_items`) but never learns from the operator's reaction to them. Two daily-use pains, both confirmed by the operator on 2026-05-31:

1. **Recurring noise.** A flag the operator considers a false alarm comes back. `risk_flags` already has `resolved_at` / `resolution_note`, but resolving an instance does nothing to stop recurrence: **Risk Watcher mints a fresh `flag_id` (UUIDv4) every run for the same `(account_id, pattern_name)`**. So "dismiss" at the instance level is a treadmill — the same account+pattern re-flags on the next scheduled run. The morning brief stays as noisy on day 90 as on day 1.

2. **Wrong-tone / off-base drafts.** When a staged draft (ADR-0060-adjacent morning-brief action staging, or a Triage/CRM-updater Task) misreads the relationship or strikes the wrong tone, that judgment evaporates. Nothing feeds it back into the next composition.

There is no capture surface for "good catch / noise / wrong tone," and no consumer if there were one. This ADR adds both, in two stages, smallest-useful-first.

The operator's stated priority is **task-level sharpening before any business-health layer**, and the consistent preference is **pragmatic, in-code enforcement over ceremony**. This design keeps the agents deterministic and vendor-portable (ADR 0051 / ROADMAP portability constraint): feedback influences emission via a SQL gate and few-shot prompt context, not via a model retrain or a new managed service.

## Decision

### §1 — New table `agent_outputs.signal_feedback`

One row per operator verdict on a signal. Keyed by the **recurring tuple**, not the instance, so suppression survives flag re-emission.

| column | type | mode | notes |
|---|---|---|---|
| `feedback_id` | STRING | REQUIRED | UUIDv4, generated by the write tool |
| `created_at` | TIMESTAMP | REQUIRED | partition column |
| `scope` | STRING | REQUIRED | `risk` \| `triage` \| `draft` (ADR 0037 scope discriminator) |
| `account_id` | STRING | NULLABLE | Airtable `rec…` id; resolved from account_name by the tool |
| `pattern_name` | STRING | NULLABLE | for `scope='risk'`: the `risk_flags.pattern_name` this applies to, matched **verbatim** by the gate. Real values are human-readable title case (e.g. `"Owner Disengagement"`), NOT snake_case — Claude echoes the exact string it saw in `open_risk_flags`. NULL = applies to all patterns on the account |
| `verdict` | STRING | REQUIRED | `noise` \| `valid` \| `wrong_tone` \| `wrong_target` |
| `note` | STRING | NULLABLE | operator's free-text ("they always go quiet in summer, ignore") |
| `mute_until` | TIMESTAMP | NULLABLE | for `verdict='noise'`: suppress through this time. NULL = indefinite |
| `source_flag_id` | STRING | NULLABLE | the specific `risk_flags.flag_id` / `triaged_items` id that prompted the verdict, for traceability |
| `created_by` | STRING | REQUIRED | always `operator` for v1 (only the operator gives feedback) |

Partitioned by `created_at`, clustered by `(scope, account_id)`. 730-day expiry to match `risk_flags`. Terraform: `terraform/modules/agent_runtime/main.tf` alongside the other `agent_outputs` tables.

### §2 — Capture surface: `record_feedback` MCP write tool

A new write tool in `mcp_server/tools/write.py`, mirroring the existing safety-wrapper pattern (`capture_note`, `insert_decision`):

```
record_feedback(scope, verdict, account_name=None, pattern_name=None,
                note=None, mute_days=None, source_flag_id=None) -> dict
```

- Resolves `account_name` → `account_id` via `airtable_replica.accounts.company_name` (same JOIN `open_risk_flags` uses).
- Forces `created_by='operator'`; computes `mute_until = created_at + mute_days` when given.
- Validates `scope`/`verdict` against the enums above (rejects anything else — prompt-injection guard, same posture as the other write tools).
- Idempotent-ish: a `(scope, account_id, pattern_name, verdict)` row created within the last 60s is treated as a duplicate and returns the existing `feedback_id` rather than inserting again.

Capture is **conversational** — no UI. The operator says "that Acme acknowledgment-gap flag is noise, mute it a month" in the Claude app; Claude calls `record_feedback(scope='risk', account_name='Acme', pattern_name='acknowledgment_gap', verdict='noise', mute_days=30)`. This is the ADR 0051 seam doing its job and is why no dashboard is needed (consistent with ADR 0059).

### §3 — Suppression gate (Stage 1, the high-value half)

When Risk Watcher goes to write a flag, `RiskFlagsWriter` first checks `signal_feedback` for an active `noise` verdict on the `(account_id, pattern_name)` tuple:

- Active = `verdict='noise'` AND (`mute_until IS NULL` OR `mute_until > CURRENT_TIMESTAMP()`).
- A row with NULL `pattern_name` mutes **all** patterns on that account; a row with a `pattern_name` mutes just that one.

On a hit, the flag is **written pre-resolved** — `resolved_at = flagged_at`, `resolution_note = "auto-suppressed: feedback <feedback_id>"` — rather than dropped. This is the load-bearing design choice, and it falls out of how the two consumers already filter:

- `open_risk_flags` (MCP read surface / morning brief) filters `WHERE resolved_at IS NULL` (`mcp_server/tools/read.py`).
- The WS-D routing fan-out poll filters `AND rf.resolved_at IS NULL` (`routing/polling.py`).

So a pre-resolved row is invisible to **both** consumers with **zero changes to either** — no Chat card, no Gmail draft, no morning-brief line — while leaving a fully queryable audit trail in `risk_flags` itself (`WHERE resolution_note LIKE 'auto-suppressed%'`), with `baseline_snapshot` still captured for replay. This is strictly better than dropping the row + writing an `agent_audit_log` event: that table is a fixed per-invocation shape with no generic event-type column, so suppression facts don't belong there. Suppression is therefore **never silent** and always reversible. A structured log line (`risk_watcher.flag_suppressed ... feedback_id=`) mirrors the existing `flag_recorded` / `flag_write_failed` logs for live observability.

Triage gets the symmetric gate for `scope='triage'` (suppress re-drafting a Task the operator has tagged noise for that account+pattern) — sequenced as a fast-follow after the Risk Watcher gate lands.

### §4 — Tuning (Stage 2, deferred until data accrues)

Once `signal_feedback` holds a few weeks of verdicts:
- **Classification few-shot:** inject recent `(account, pattern, verdict, note)` rows as few-shot examples into the Risk Watcher / Triage classification prompts ("the operator considers these noise / these valid"). Keeps the LLM call SDK-thin and model-swappable — no fine-tune, no new dependency.
- **Tone guide:** `verdict='wrong_tone'` notes accumulate into a learned style-guide note (`scope='personal'` in `notes`, retrievable by `brain_ask`) that the morning-brief composer and any draft-writing routine read before composing. Seed it from the existing "field note in the operator's voice" routine.

Stage 2 is explicitly **not** in the first build — ship §1–§3, live with it, and only add tuning if suppression alone doesn't quiet things enough.

## Consequences

- **Positive:** recurring false-alarm flags stop recurring with one conversational sentence; suppression is auditable and time-boxed (`mute_until`), not a permanent silent blocklist; no new service, no new dataset, no managed-ML — fits the $50/mo budget (ADR 0024) and the portability constraint.
- **Negative / watch:** the suppression gate is a new pre-emission code path in Risk Watcher — needs the "smoke-fire the conditional path against real data" discipline from CLAUDE.md (a gate that only fires when a matching feedback row exists won't surface bugs until one does). Over-muting could hide a genuine turn-for-the-worse; `mute_until` defaulting to a finite window (suggest 30d) when the operator doesn't specify mitigates this.
- **Rejected — resolve-the-instance only:** doesn't stop recurrence (the `flag_id`-per-run behavior is the whole problem). The §3 gate is the tuple-keyed generalization of instance-resolve: it pre-resolves *future* emissions of the muted tuple, not just the one the operator clicked.
- **Rejected — drop the flag + emit an `agent_audit_log` event:** the audit table is a fixed per-invocation shape with no event-type column; pre-resolving the row keeps the audit trail in `risk_flags` where it's already queryable and reuses the consumers' existing `resolved_at IS NULL` filters (zero consumer changes).
- **Rejected — a managed feedback/RLHF pipeline:** enterprise ceremony for a 2-person tool; few-shot + a SQL gate gets ~all the value at ~none of the cost.

## Build sequence

1. §1 table + §2 `record_feedback` tool + unit tests (local MCP server redeploy — stdio subprocess, no image). `terraform apply -target` the new table.
2. §3 suppression gate in Risk Watcher + Triage; smoke-fire against a real seeded `noise` row before merge; `risk-watcher` + `triage-bridge` image rebuilds.
3. §4 tuning — separate PR, after data accrues (~mid-June 2026 review window).
